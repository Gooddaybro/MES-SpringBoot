# R006之后：先完成受控建单，再扩展生产能力

2026-11-02。本文是规划，未实施项不能写成当前能力。第一批实测见[能力与验收](R006-能力盘点与第一批验收.md)。

## 第二批：最值得优先完成的建单闭环

现有 WorkOrderService 已能在Java事务中建单并保存完整路线快照，也有同号幂等和独立状态转换。缺的是自然语言草稿、预检查、服务端预览凭据、人工确认及确认时重新校验，而非重新实现工单表。

建议顺序：

1. 复用名称搜索给出候选，要求用户明确物料编码；提取数量及原业务要求的工单号。当前表没有计划日期或优先级字段，未建模前不填造默认值。
2. Java只读预检查正常物料、基本单位、完整路线、参数、工单号冲突及Shiro写权限。库存、BOM齐套、产能列为“未检查/缺可信数据”，不能列为通过。
3. 展示物料、数量、真实工序、拟执行动作及未检查项。预览不调用create。
4. Java保存与登录主体、精确参数、路线摘要绑定的短期确认凭据。确认凭据一次消费，幂等执行结果需要可恢复，不能仅保存在Python内存或依赖模型文字。
5. 用户点击“确认创建”后，Java重新核验登录、权限、参数、物料及路线摘要；变化则要求重新预览。复用原create事务，返回实际编号及冻结快照。
6. 在3308独立学习环境完成正常、无路线、权限撤销、过期、重复点击、并发确认及路线变化的验收；未经授权不对3307补种工艺或创建工单。

数据库：优先保留mes_work_order结构；确认凭据和执行结果若需持久化，新增专用请求记录表及下一可用Flyway迁移（实施时核对版本，本文不预占版本号）。至少记录请求标识、主体、参数摘要、工艺摘要、过期时间、执行状态及实际工单ID。不存明文模型Key或共享签名密钥。多实例幂等不能只靠浏览器禁用按钮。

当前3307只有电工胶带及失效的路线引用，尚不具备可靠建单前提。3308的SERVO-DEMO-*明确为教学数据，可验证工程闭环，不能宣称工厂投产验收。

## 展示和验收的边界

优先展示“真实记录检索→受控校验→预览→人工确认→Java事务→数据库核验”的单个闭环，其次是可解释、可回溯的快照对比。工单数量不是产能，状态不是报工实绩；没有工时、设备负载、班次及排程时，不声称可准确预测瓶颈、插单影响或交期。
